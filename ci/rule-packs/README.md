# Rule-pack authoring checks

P2-02 provides an approval-aware lookup for the citation register. The owner approved the current wording in principle on 5 November 2026, with legal counsel's review pending. `approvedCitation(register, category)` returns a copy of the citation only when register/category status and reviewer/date metadata agree. Approval in principle additionally requires an explicit pending legal review; it does not claim counsel has approved the wording. A draft, unknown or duplicate category, missing wording or absent review metadata throws an error. This is an authoring helper, not a substitute for human or legal review and not a product runtime dependency.

Run `node --test ci/rule-packs/citations.test.mjs` with Node.js 26. Tests use synthetic approval metadata to exercise the lookup; the committed status records the owner's instruction, not an automated approval. The [review page](../../rule-packs/CITATIONS.md) explains the official source pins and approval process. The register is not itself a rule pack.

P2-03 adds `node --test ci/rule-packs/identifier-cases.test.mjs` for the corpus-first identifier matrix and byte-exact regeneration. Its generated inputs and pending production acceptance are documented in [IDENTIFIER-ACCEPTANCE.md](../../rule-packs/IDENTIFIER-ACCEPTANCE.md).

P2-04 adds `node --test ci/rule-packs/location-cases.test.mjs` for the five-location matrix and field handling in every launch stack. Its generator reuses the identifier case builder and synchronisation function. [LOCATION-ACCEPTANCE.md](../../rule-packs/LOCATION-ACCEPTANCE.md) records severity and rule-composition decisions still needed before production acceptance.
P2-03 implementation cards add authoring modules under `rules/`. Run `node build-detection.mjs --write` from this directory to generate schema-valid unsigned source packs, rule reference pages and additional corpus cases; use `--check` to verify them. `detection.test.mjs` checks every generated byte through the existing pack assembly validator. The builder requires descriptions, limitations and remediation before producing a reference page. It copies only owner-authorised citations. Synthetic identifiers come from the documented generator; no dependency, signature or release is added.

P2-07-03 adds `./ci/rule-packs/Measure-Detection.ps1 -WriteReport` from the repository root to regenerate [synthetic-measurements.md](../../docs-data/synthetic-measurements.md). Omit `-WriteReport` to verify the committed report. The command runs `DetectionPackTests` through the existing test infrastructure. Every authored pack is verified with an in-memory development signature; all synthetic repositories run against the combined rules. Missing/invalid packs, duplicate rules, unexpected findings, missed synthetic expectations and stale reports fail. Every loaded rule appears, including zero-finding rules. Exact per-rule and overall error gates use the existing scorer. The report pins source digests and explicitly leaves real-repository owner triage unmeasured. Regenerate it after any source pack or corpus change; the normal corpus suite verifies it in CI.

The processor catalogue includes Nigerian payments, wallets, banking-service references and identity-verification integrations alongside cloud services. Each new token needs an official technical source, an exact positive and a longer-token near-miss before its rule is added. `ProcessorCatalogue_Should_ReportTheNamedProvider` independently requires the Interswitch, PalmPay, OPay, NIBSS, Monnify, Remita, Korapay, Dojah and Youverify entries, so deriving the generated cases from an incomplete list cannot hide their omission. NIBSS coverage uses the public e-invoicing API hosts and Java SDK artefact; a portal-only reference has an explicit negative case. Other private API/VPN endpoints remain outside the verified catalogue. All entries remain notes; service references do not establish processing, legal role, region or a transfer.
