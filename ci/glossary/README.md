# Banned-terms lint

The banned-terms lint drives rule 4 of `AGENTS.md` (glossary conformance, NFR-028). It reads the machine-readable glossary at `docs/glossary.json` and flags banned vocabulary and banned name variants in prose and in identifiers. Continuous integration wiring for this lint belongs to P0-12; this folder provides the lint and proves it works.

## The glossary

`docs/glossary.json` is the source of truth. It has three parts:

- **`terms`** — approved vocabulary. Each entry has the approved `term`, a `definition`, a list of `banned` alternatives, and an `appliesTo` of `prose`, `identifiers` or `both`. The lint flags each banned alternative wherever the `appliesTo` scope says it applies.
- **`nameForms`** — the five approved name forms and what each is used for. These are documentation for now; the lint's messages point at them. A future change may add a check that a form appears only in its approved scope.
- **`bannedVariants`** — the wrong spellings of the product name and the binary. Each entry has the `variant`, an `appliesTo`, a `caseSensitive` flag, and an optional `allowedSuffixes` list so that a longer, correct name is not caught (for example `gatekeeper-ndpa` must not catch the correct binary `gatekeeper-ndpa-check`).

The glossary is hand-maintained source data. It is derived from the Gate-Keeper product glossary (Doc 15) and the name-form convention the owner decided on 28 October 2026. It is not regenerated by a build step, because its source document is not in this repository.

## Matching rules

- Vocabulary `banned` alternatives are matched case-insensitively as substrings, so `ruleset`, `Ruleset` and `ruleSet` are all flagged.
- Name `variant`s are matched case-sensitively or case-insensitively according to their `caseSensitive` flag, as substrings, so `GatekeeperService` and `gate_keeper_flag` are caught.
- Files are classified by extension: prose files (`.md`, `.txt`, `.html` and similar) receive `prose` and `both` rules; code and data files (`.cs`, `.ts`, `.json`, `.ps1` and similar) receive `identifiers` and `both` rules; anything unknown receives every rule. This classification is deliberately coarse: a comment inside a code file is treated as an identifier, which is an accepted simplification for version 1.0.0.
- Multi-word banned terms such as `compliance score` are matched as the literal phrase. The compacted identifier form (`complianceScore`) is not matched in version 1.0.0.

The glossary file itself and the fixtures necessarily contain the banned strings, so a repository-wide scan must exclude `docs/glossary.json` and `ci/glossary/fixtures/`. P0-12 decides that exclusion list when it wires the lint into continuous integration.

## Commands

Flag the fixtures that contain banned terms (exits 1 and lists each finding):

```powershell
pwsh ./ci/glossary/Invoke-GlossaryLint.ps1 -Path ci/glossary/fixtures/banned-terms.md,ci/glossary/fixtures/banned-terms.cs
```

Prove the lint works, including that conforming fixtures are clean:

```powershell
pwsh ./ci/glossary/Test-Glossary.ps1
```

The lint exits 0 when nothing is flagged, 1 when it flags a banned term or variant, and throws on a tool error such as a malformed glossary or a missing path.

## Finding format

Each finding is one line on the standard output stream, in this shape:

```text
relative/path:line:column: banned "ruleset"; use "rule pack"
```

Paths use forward slashes and are relative to the repository root. Findings are sorted by path, line, column and text so that the output is byte-for-byte deterministic.
