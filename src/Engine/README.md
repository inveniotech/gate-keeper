# Rule engine

The rule engine library shared by the command-line interface and the .NET middleware. Work package P1-01 (issue #11) added the immutable domain types the later Phase 1 work builds on: the pack loader (P1-03) fills rules with matchers, the matcher engine (P1-06) produces findings, and the scan orchestrator (P1-07) assembles scan results. Work package P1-05 (issue #15, IQ-21 and IQ-83) added the file enumerator, so the scan input is now the engine's too.

Work package P1-08 (issue #18) added the configuration loader: it locates and reads the settings file `.ndpa-check/ndpa-check.toml` (IQ-02), parses it through Tomlyn under NativeAOT, validates every key the configuration specification lists, and resolves the effective `ScanSettings` with the profile defaults of `default` and `deep` (IQ-23).

Work package P1-06 (issue #16, IQ-12 and IQ-14) added the matcher engine. It compiles each structured shape into one cached `NonBacktracking` regular expression with a match timeout, runs the closed validator set, keeps a match only when a context keyword sits within the rule's window, honours file-location paths and stamps the rule's location kind, copies suppression hints through as help text, and matches list entries only as whole tokens so a shorter package name or hostname does not match inside a longer one.

Work package P1-03 (issue #13) added the pack loader: it turns pack bytes into the merged rules, verifying the Ed25519 signature over the exact manifest payload bytes, checking both content digests, reading and validating the content document with a hand-written reader (no reflection-based schema library under NativeAOT), checking the pack-line facts, admitting each pack through `IPackEntitlementPolicy`, and merging under IQ-24. A tampered, malformed or incompatible pack fails loudly with `EngineToolException`, which the scan orchestrator maps to exit code 2 — unlike licence problems, which degrade quietly (rule 13).

## Public contract

- The immutable domain types in this folder's `.cs` files: `RulePack`, `Rule`, `Citation`, `RedactionOptions`, `ProcessorInfo`, `Finding`, `Location`, `Fingerprint`, `ScanResult`, plus the closed enums `Severity`, `BaselineState`, `LocationKind`, `PackProvenance` and `ExitOutcome`. Every type is a `sealed` record, its lists are read-only, and its constructor validations match the results format and the rule-pack format (1-based lines and columns, 64-character lowercase hexadecimal fingerprints).
- `Rule` carries its matcher: `RuleMatcher` holds exactly one of `RulePatternMatcher` (shape parts, boundary, optional named validator, prefilter keywords and window, location, exclusions) or `RuleListMatcher` (exact package and hostname entries). `RuleShapePart` is one atom — a `literal`, a `class`, `ranges` or an `oneOf` alternation — with `min`/`max` repetitions and at most one `emit` per shape; `RuleValidator` names one of the closed validators `digits-length`, `nuban`, `ng-phone-prefix` or `email-not-example-domain`, carrying `length` or `prefixes` as pack data where the validator needs them (rule-pack format sections 4, 5 and 7 to 8).
- `PackLoader.Load(signedPacks, localPacks, keyCatalogue, entitlementPolicy)` is the one entry point. A `SignedPackInput` carries the specification's byte sequences directly — the content bytes, the manifest armour with its 64-byte signature, and an optional detached watermark — because the released-pack container is defined when the pack build step (P2-03) lands. A `LocalPackInput` carries the unsigned content bytes of a pack the repository configuration lists (IQ-25). The verification order is the format's order: armour, manifest, signature, both digests, content (schema version, shape bounds, the scalar-value sum, and every schema check), manifest agreement, engine version, the pack-line facts, entitlement, then the merge.
- The merge (IQ-24) keeps the greatest version of a pack identifier as a whole, refuses two copies of the same version with different content digests, refuses a rule identifier two different packs claim, and refuses a local pack claiming an Invenio pack identifier (IQ-25). The `MergedRules` result records every surviving pack with its provenance (`bundled`, `plan-gated` or `local`) and content digest, plus every rule with its pack, in ordinal identifier order, so two identical loads give the same bytes (rule 6).
- `IPackKeyCatalogue` maps a manifest or watermark `keyId` to the 32-byte embedded public key/an unknown key never verifies anything. `IPackEntitlementPolicy` decides which provenance a build may load, and the MVP implementation `BundledPacksOnlyPolicy` refuses plan-gated packs with the sentence the user sees: Phase 5 replaces it without changing the loader (IQ-10).
- The pack vectors under `tests/vectors/pack/` are generated from `New-PackVectors.mjs` with two clearly labelled development-only keys, `gkpk-dev-1` (pack signing) and `gkwm-dev-1` (the detached watermark, a different key because the spec checks the block separately). Production keys are never in this repository, and keys are never logged (rule 14).
- `ConfigurationLoader.Load(rootPath)` reads `.ndpa-check/ndpa-check.toml` and returns `ConfigurationLoadResult`: the effective `ScanSettings` or null, with warnings (such as an unknown key, IQ-17) and tool-error sentences in en-GB. When the file is absent every section 4 default applies. An unknown key warns and never fails; a known key with the wrong value, a wrong `schemaVersion`, a byte-order mark, an oversized file or invalid TOML is a tool error. The loader never walks parent directories and never writes the file back.
- `ScanSettings` carries every key of the settings file, resolved: `Profile`, `ScanHistory`, `MaxFileBytes`, `Exclude`, `IncludeSubmodules`, `RepositoryId`, `BaselineMaxAgeDays`, `FailOn`, `SeverityOverrides`, `DisabledRules` and `LocalPacks`. `ScanProfile` is the closed set `default` and `deep` (IQ-23); `DisabledRule` carries the written reason IQ-24 requires.
- `ScanSettingsToml` is the typed model of the settings file and the Tomlyn source-generated `TomlSerializerContext` for it (IQ-17): reflection stays disabled under AOT (rule 7).
- `EngineProduct` stamps the facts every artefact carries (NFR-031): the product name `gatekeeper`, the engine version, and the bundled rule pack version, which is `null` until the pack build step bundles one, so the version output states the absence rather than inventing a number.
- `EngineJsonSerializerContext` is the System.Text.Json source-generation context for every serialised type. There is no reflection-based serialisation anywhere in the engine or the interface (rule 7).
- A finding never carries the matched value as data. Outputs name the rule and the location (rule 10).
- `FileEnumerator` is the one enumeration of the scan input (sections 6 and 7 of the configuration specification). Inside a git work tree it lists the files the index tracks (`git ls-files`), and outside one it walks the directory, applies the `.gitignore` semantics for every `.gitignore` in the tree and records the `scan.outside-git` warning. The built-in exclusions (the excluded directory segments, the lock-file names and the minified-file names), the `scan.exclude` globs (`PathGlob`, sections 6.3 and 5.3), the per-file byte limit, the binary probe (a NUL byte in the first 8,192 bytes), the encodings UTF-8 and UTF-16 with a byte-order mark, the Git LFS pointer skip, the un-checked-out submodule warning, the `--changed-since` work-tree limit and, on request, the history blobs reachable from `HEAD` are all the enumeration's work. When `git` is not installed at all, the enumeration degrades to the directory walk and records the `scan.outside-git` warning, because git is guaranteed on the runners the product targets and silent absence at a customer site must still produce an honest determinable result.
- The enumeration hands `FileEnumerationResult` to the caller: `Files` (the scanned work-tree files with their decoded text, in ordinal path order), `History` (the history candidates with the 40-character commit identifier of the newest commit whose tree still contains the blob, the path, and the decoded text, in commit identifier then path order), `Warnings` (the closed-set notices the evidence file records, in code then message order) and `Notes` (the skip sentences for binary, oversized, LFS pointer, non-UTF-8 and unreadable candidates, in ordinal path order). All paths are forward-slash, relative to the repository root and Unicode-normalised to Normalisation Form C (rule 22).
- `HistoryCandidate` and the history list exist so the scan orchestrator (P1-07) can run the matcher over historical bytes and emit the `history` array the results format defines: they are a scan input, never a finding, and they carry no fingerprint and no baseline state (IQ-83).
- `MatcherEngine.Match(path, text)` runs the rules it was given and returns `RuleMatch` values sorted by line, column, rule identifier and span length. A match carries the rule, the 1-based line and column, the location kind and the span indexes the fingerprint step needs. It does not carry the matched text (rule 10). `suppressionHints` are copied onto the match and are never read as an instruction. A keyword is an ASCII-folded substring, so `bvn` inside `customerBvn` counts, and the window is the gap in scalar values on either side of the shape. `location.paths` uses the same glob subset as `scan.exclude`; `location.kind` is the kind the match reports, or `source` when the rule names none. The engine does not guess that a line is a log call: that heuristic is pack data (P2-04). The list matcher treats ASCII letters, digits, `.`, `-`, `_` and `+` as one token. A rejected pattern match resumes one scalar value later; an accepted match resumes at its end (section 7.5). A shape past the section 7.1 bounds, a keyword list with no window, or a validator the registry does not carry fails at construction with `EngineToolException`.
- `RuleValidatorRegistry` is the closed set `digits-length`, `nuban`, `ng-phone-prefix` and `email-not-example-domain`. `nuban` checks the Central Bank of Nigeria serial weights the corpus pins to bank code `011`. `email-not-example-domain` refuses `example.com`, `example.net`, `example.org`, `test`, `invalid` and `localhost`, including subdomains. It does not refuse the `.example` top-level domain, because the golden corpus's positive email case uses `ledger-ops.example`.
- `EngineToolException` is the one tool error the engine throws: the message is the complete en-GB sentence the console shows, and the exit-code mapping stays in the CLI (rule 13, rule 23). Every pack loader failure raises it, naming the pack and the reason.
- `PathGlob` compiles and matches the `scan.exclude` glob subset; `FileEnumerationOptions` validates its values at construction, before any file is read (rule 28).

## Dependencies

`Tomlyn` (BSD-2-Clause, approved under rule 8 of `AGENTS.md`; pinned in `Directory.Packages.props`): the settings file is TOML, and Tomlyn parses it through a source-generated TomlSerializerContext, so the CLI stays NativeAOT-clean. The engine also references the signing module (the internal signature assembly): the pack loader verifies pack and watermark signatures through the verifier factory the signing module exposes, and the engine is listed in that module's `InternalsVisibleTo` like every other consumer. `System.Text.Json` ships in the .NET shared framework, so no package is added for it. The pack content reader is hand-written, so no JSON Schema library is pulled into a shipped component (the test-only `JsonSchema.Net` stays in the schema tests). The enumeration shells out to the `git` executable, which is required on every runner the product targets; there is no network access anywhere in the engine (rule 5), and `git` is asked for objects the local object database already holds, never to fetch (IQ-21).

## How to test

`DomainSnapshotTests` checks source-generated snapshots of rules, complete packs
and merged load results. Round trips preserve matching, exclusions, optional
metadata, selected pack provenance and exact deterministic JSON. Value-object
snapshots use explicit reflection-free converters: positional record members
and validated properties otherwise collide under camel-case naming. The
converters retain existing public members and reapply coordinate and fingerprint
validation on read. They do not change the evidence or pack wire formats, whose
dedicated readers and writers remain authoritative.

From the repository root:

```powershell
dotnet test --filter FullyQualifiedName~Engine.Tests
```

The enumerator's tests build real throw-away git repositories under the machine's temporary directory with fixed author identities and fixed commit dates, so the object identifiers are byte-stable across machines and runs (rule 26). One test skips itself when the machine does not grant the symbolic-link privilege the fixture needs.

The pack loader's tests (`PackLoaderTests`) read the committed vectors under `tests/vectors/pack/`, which `node tests/vectors/pack/New-PackVectors.mjs` regenerates; the signed scenarios run every content-level check behind a verified signature, exactly as a real pack arrives. The local-pack scenarios write small unsigned documents with synthetic identifiers (rule 10).

## Scan orchestration (P1-07)

The matcher conformance-vector tests and shape-compiler tests that execute matches explicitly disable the regular-expression deadline: they check exact semantic outcomes independently of runner scheduling and cold-start time. Production keeps its 100 ms default deadline. Separate `ShapeCompilerTests` assert that the production default is exactly 100 ms and that default and explicitly configured timeouts are carried by the compiled regular expression. `NonBacktracking` enforces finite deadlines even though its matching algorithm is linear. Semantic tests still assert exact alternatives, case folding, literal repetition and emitting spans; their results do not depend on hosted-runner timing.

`ScanOrchestrator` accepts a prepared `MatcherEngine` and scans either `FileEnumerationOptions` or an existing `FileEnumerationResult`. File selection and decoding remain with `FileEnumerator`. Work-tree reads and matching use at most `Environment.ProcessorCount` workers. Each worker owns its collections; the caller merges them only after all workers finish. History blob reads retain the enumerator's serial Git batch protocol.

The returned `ScanMatchResult` contains work-tree `RuleMatch` values sorted by ordinal path, line, column and rule identifier, plus separate `HistoryMatch` values ordered by commit identifier, path, line, rule identifier and column (results format section 5.4, IQ-83). It retains enumeration diagnostics for the caller. This is an intermediate result: never serialise the enumeration, which carries source text. Policy, fingerprints and evidence writers remain later stages; `ScanResult` and its serialised contract are unchanged. Cancellation and tool errors propagate without returning partial findings. Concurrent scans share only prepared read-only matchers. No output is written by the orchestrator.

Run `dotnet test tests/Engine.Tests --filter FullyQualifiedName~ScanOrchestratorTests` for shuffled-input byte equality, exact ordering, history separation, cancellation, concurrent calls and directory integration. The whole-process benchmark in quality-budgets section 6 needs the scan command, embedded pack and P1-15 harness; these are not provided by this engine card.

## Exceptions and baseline (P1-09)

`PolicyStore.LoadAsync` validates root-local exceptions, baseline entries and the fingerprint key. It rejects unknown exception fields, unknown scopes, duplicate identifiers or fingerprints, invalid dates, invalid key bytes and oversized input without printing file contents. `FindingPolicy.Apply` uses the explicit evaluation date to apply rule exceptions before category exceptions, rejects equal-rank ambiguity, records every application, and leaves baselined findings visible. `PolicyResult` carries the evaluation date, applied exception hashes and debt summary for the results writer. A missing key omits fingerprints and leaves findings new, with the specified warnings.

`BaselineCommand.RunAsync` uses the existing enumerator and matcher, ignores history, creates an absent random key, ensures the key is gitignored, and atomically rewrites the surviving fingerprints while preserving their original dates. New keys use owner-only Unix permissions or an owner-only protected Windows access-control list, established before key bytes are written. The key is never overwritten or emitted. `FingerprintCalculator` implements the fixed keyed message from configuration section 13.2 because baseline identity needs it; output writers reuse this calculation. `EvaluationDate.Resolve` accepts an explicit date, an epoch input or an injected clock, in that order. Expiry and baseline age deliberately depend on this date; the same explicit date keeps policy deterministic across runs.

Run `dotnet test tests/Engine.Tests --filter FullyQualifiedName~FindingPolicyTests` for expiry and age boundaries, strict input validation, scope precedence, published hash vectors, key preservation and repeatable baseline bytes.

## Results writers (P1-11)

`ResultsWriter.Write` consumes a completed `ResultsInput` and returns the two UTF-8 documents as `ResultDocuments`. It rejects tool-error outcomes, inconsistent history state and missing Invenio coverage dates before returning any output. The host supplies repository identity, revision, effective settings and outcome; no clock, fingerprint key or source text reaches the writer. P1-10 supplies the failure-threshold decision. Findings, exceptions, packs, warnings and inventory groups are sorted explicitly, and both documents use two-space indentation, LF line endings and a trailing newline. The engine version is stamped from `EngineProduct`; both documents retain each loaded pack version, digest and coverage date. SARIF stores these stamps in the ordinally sorted `properties.packs` array, using the same metadata as evidence, even for a pack that produced no findings. Engine versions identify scanner code; pack versions and digests identify the independently changing detection rules and exact payload. Each artefact therefore remains auditable when retained on its own. Schema artefact 1.2.0 accepts the additive SARIF property while continuing to accept older logs without stamps. `LoadedPack.CoverageDate` now retains that existing pack fact for the writer without changing its positional constructor.

SARIF is built with the approved `SarifKit` models and `SarifWriter`. A final JSON projection enforces the closed profile's property order and excludes library defaults outside that profile. Property bags use ordinal sorted keys. Work-tree findings alone enter SARIF; historical matches stay in evidence. Baseline state and optional keyed fingerprints carry through unchanged, and inventory counts only reported work-tree findings. Suppressed findings have only exception-application evidence. No matched values, snippets or secret keys enter either document. The fingerprint helper added for baseline in P1-09 is the one computation reused by this pipeline.

Run `dotnet test --filter FullyQualifiedName~ResultsWriterTests` for empty and populated documents, exact evidence fields, baseline state, suppression evidence, negative official-schema validation and byte equality under shuffled input. The official schema is a pinned offline fixture under `tests/vectors/sarif/`; its README gives the regeneration command.

## Severity and exit decisions (P1-10)

`SeverityPolicy.Evaluate` is the failure-threshold decision over a completed `PolicyResult`: error fails on errors, warning includes warnings and errors, and note includes all three severities. Baselined work-tree findings remain visible without failing; historical findings can fail and never use baseline state. Suppressed and disabled findings have already been removed by policy. `ValidateSettings` rejects overrides or disabled identifiers absent from the loaded packs before matching. Baseline now reuses this validation.

`SeverityPolicy.RunAsync` wraps the host's asynchronous scan operation and returns a `ScanDecision`. Successful scans return pass or violations, mapping to process codes 0 or 1. Known tool or repository-access failures return code 2 and an actionable diagnostic, with no partial result to serialise. Cancellation propagates. Licence state is not an input to the decision. The command host writes diagnostics to standard error and passes only completed results to the writers. CLI scan-command wiring remains its separate card.

Run `dotnet test tests/Engine.Tests --filter FullyQualifiedName~SeverityPolicyTests` for all 144 combinations of severity, threshold, baseline state, suppression, history and tool errors, plus cancellation, repository access errors, effective override order, invalid settings and evidence/SARIF exit-code agreement.

## Repository metadata (P1-12)

RepositoryMetadata reads local Git facts through the existing Git runner. It normalises remote identities under configuration section 10 and removes remote credentials before evidence is produced. Its pure normalisation tests cover HTTPS, SSH, SCP-style remotes and local paths. No remote objects are fetched.

## Rule-pack age (P1-14)

LoadedPack retains the verified content issue date separately from its coverage date. PackAgeWarning.Evaluate compares the newest loaded content date with the declared evaluation date. It returns the existing pack.stale warning only after 90 civil days; undated local packs do not invent an age. The CLI includes this warning on standard error and in evidence JSON. Boundary tests use an injected clock and cover 89, 90 and 91 days, future dates and mixed pack dates.

## Optional benchmark instrumentation (P1-15)

Only builds with BenchmarkInstrumentation=true include anonymous per-file matching times, per-thread allocation deltas and per-rule regex search counters. The counters retain no source path or matched value. Normal release builds contain neither these types nor their counters. The same existing matcher and orchestrator run in both modes, and instrumented tests prove exact regex call and input-byte counts while retaining identical findings. Input bytes count the UTF-16 searchable suffix for every search, including unsuccessful searches.
## Installation Git checks (P1-13)

RepositoryGitState reuses the local Git runner to check executable availability, work-tree membership and whether the index tracks the fingerprint key. It never reads key contents or contacts a remote. Tests exercise an indexed synthetic key and a plain directory.
