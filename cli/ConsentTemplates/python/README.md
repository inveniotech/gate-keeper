# FastAPI consent starting point

Generated by Gate-Keeper {{version}} (P3-06, F-005, UC-003). This helper applies only to processing whose lawful basis is consent.

Use the host application's `inveniotech-gate-keeper` package. Create one provider per application and expose the synchronous check as a FastAPI dependency:

```python
from fastapi import Request
from inveniotech.gatekeeper.consent import ConsentCheck
from consent.consent_provider import EventConsentProvider

provider = EventConsentProvider(application_clock)
app.state.consent_provider = provider
app.state.consent_check = ConsentCheck(provider, None, safe_diagnostic)

def consent_check(request: Request) -> ConsentCheck:
    """Supply the application-owned check to Depends(consent_check)."""
    return request.app.state.consent_check
```

`application_clock` is the host's `Callable[[], datetime]` clock and must return an offset-aware time; use a fixed UTC time in tests. `safe_diagnostic` receives only purpose/type metadata and must never log subject identifiers. Use `Depends(consent_check)` in existing synchronous handlers. Call `provider.record(subject_id, purpose, granted, channel, notice_version)` after authorising the request. Pass `True` to grant and `False` to withdraw through the same flow. Use `check.is_granted(subject_id, purpose)` at the processing boundary. Only granted permits consent-based processing. If replacing the store with blocking database calls, keep it in synchronous FastAPI handlers; an asynchronous store must implement the adapter's asynchronous provider contract instead.

The store appends `granted` and `withdrawn` events with the subject identifier, namespaced purpose, UTC time, channel and notice version. The latest appended event for that subject and purpose determines current state; no record means denied. `history()` returns a tuple of immutable events. Verify grant, withdrawal, re-grant and separation between subjects and purposes with a fixed clock.

This store is an in-memory example: restarting the application loses every event, and different processes have separate histories. Replace it with application-owned durable, concurrency-safe storage before deployment. Keep the append-only ordering and all event fields. Authorise each request against the authenticated subject, validate input and the notice/channel against application policy, and protect history access. Do not log subject identifiers or history. The scaffold installs no routes, user interface, database or dependencies and edits no existing application files. Wire granting and withdrawal into the application's existing authenticated flow.
