# Spring Boot consent starting point

Generated by Gate-Keeper {{version}} (P3-06, F-005, UC-003). This helper applies only to processing whose lawful basis is consent.

Use the host application's `africa.gatekeeper:gate-keeper-core` dependency. Copy `ConsentProvider.java` into the application's Java source tree under `consent/`. It uses Java 17, the Spring Boot integration's runtime floor. Add these bean methods to an existing Spring configuration:

```java
@Bean
consent.ConsentProvider consentProvider(java.time.Clock clock) {
    return new consent.ConsentProvider(clock);
}

@Bean
africa.gatekeeper.ConsentCheck consentCheck(consent.ConsentProvider provider) {
    return new africa.gatekeeper.ConsentCheck(provider, (purpose, errorType) -> {
        // Route only the safe purpose/type diagnostic to your logger.
    });
}
```

Supply the application's `Clock` bean and use `Clock.fixed(...)` in tests. Inject the provider into an existing authenticated handler and call `record(subjectId, purpose, granted, channel, noticeVersion)`. Pass `true` to grant and `false` to withdraw through the same flow. Inject `ConsentCheck` at the processing boundary and use `isGranted(subjectId, purpose)`. Only granted permits consent-based processing.

The store appends `granted` and `withdrawn` events with the subject identifier, namespaced purpose, UTC time, channel and notice version. The latest appended event for that subject and purpose determines current state; no record means denied. `history()` returns an immutable copy. Verify grant, withdrawal, re-grant and separation between subjects and purposes with a fixed clock.

This store is an in-memory example: restarting the application loses every event, and different processes have separate histories. Replace it with application-owned durable, concurrency-safe storage before deployment. Keep the append-only ordering and all event fields. Authorise each request against the authenticated subject, validate input and the notice/channel against application policy, and protect history access. Do not log subject identifiers or history. The scaffold installs no routes, user interface, database or dependencies and edits no existing application files. Wire granting and withdrawal into the application's existing authenticated flow.
