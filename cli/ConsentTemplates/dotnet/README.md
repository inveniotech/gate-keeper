# ASP.NET Core consent starting point

Generated by Gate-Keeper {{version}} (P3-06, F-005, UC-003). This helper applies only to processing whose lawful basis is consent.

Reference the Gate-Keeper .NET middleware in the host application and import the namespace used by `ConsentProvider.cs`. Register one store and reuse it for all requests in `Program.cs`:

```csharp
builder.Services.AddSingleton<TimeProvider>(TimeProvider.System);
builder.Services.AddSingleton<ConsentScaffold.ConsentProvider>();
builder.Services.AddSingleton<IConsentProvider>(
    services => services.GetRequiredService<ConsentScaffold.ConsentProvider>());
builder.Services.AddSingleton(services => new ConsentCheck(
    services.GetRequiredService<IConsentProvider>(),
    diagnostic => { /* Route only the safe purpose/type diagnostic to your logger. */ }));
```

Inject `ConsentScaffold.ConsentProvider` into the application's existing consent handler and call `RecordAsync(subjectId, purpose, granted, channel, noticeVersion, cancellationToken)`. Pass `true` to grant and `false` to withdraw through the same application flow. Inject `ConsentCheck` wherever the application checks consent. Only `ConsentState.Granted` permits consent-based processing.

The store appends `granted` and `withdrawn` events with the subject identifier, namespaced purpose, UTC time, channel and notice version. The latest appended event for that subject and purpose determines current state; no record means denied. `History()` returns a copy and never changes the store. Use a fixed `TimeProvider` in tests to verify grant, withdrawal, re-grant and separation between subjects and purposes.

This store is an in-memory example: restarting the application loses every event, and different processes have separate histories. Replace it with application-owned durable, concurrency-safe storage before deployment. Keep the append-only ordering and all event fields. Authorise each request against the authenticated subject, validate input and the notice/channel against application policy, and protect history access. Do not log subject identifiers or history. The scaffold installs no routes, user interface, database or dependencies and edits no existing application files. Wire granting and withdrawal into the application's existing authenticated flow.
